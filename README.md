# SheetMate · 通用 Excel Agent

具备**分析、修改、重复执行、建表**四大能力的 Excel 助手：既能处理已有工作簿，也能根据用户提供的内容从零生成带格式的 Excel。本地部署，数据只在你的电脑上，只要配置一个 DeepSeek API Key 就能用。

- **自动理解需求**：直接描述需求，后端 AI 每轮结合当前要求、历史和资料，自动判断分析、修改或建表，已有流程通过 Recipe 重复执行，无需前端切换能力。
- **公式和 SQL 优先**：内置公式、DuckDB SQL 和 Python 脚本是三类独立工具，可混合使用。AI 优先用公式或 SQL 完成清洗、筛选、计算、匹配和汇总，只有它们不好做或能力范围之外的特殊结构、复杂布局或算法才用脚本；明确超出范围时无需先试错。按真实数据结构、规模和交付要求比较稳定性、性能、准确性，混合任务只为需要的部分写脚本。
- **从零建表**：把文字描述、粘贴的资料、口述转成的文字或已读取的表格内容整理成新 Excel，无需先上传模板。支持多 sheet、合并单元格、多行表头、边框、底色、行高列宽、数字格式、冻结窗格和明确指定的 Excel 公式。没有提供的数据留空，用户明确要求模拟时才生成示例数据。
- **副本辅助处理**：不管是读取、分析还是修改，都可以按需生成独立分析副本，去格式化、拆合并或转换成工具方便处理的数据，用公式、SQL 或脚本筛选、计算和生成中间表，辅助分析或修改。原件始终只读；修改结果由 Recipe 或脚本写入另一份原格式工作簿副本，分析副本不代替最终修改交付。
- **统计查询**：原始文件只读，先复制原文件和数据到独立临时工作区；分析副本可以去格式化、拆合并或转换成方便工具使用的数据，再按需筛选、计算。结束、失败或停止后清理临时副本，原文件、已展示的结果表和明确导出的结果保留。
- **编辑表格**：独立保留一份原格式工作簿副本用于修改和交付；可先在隔离的分析副本中自由筛选、计算、核对和准备中间数据，再把确认的修改步骤交给 Recipe，或让脚本在原格式文件副本上完成。重复执行和断点重跑也使用副本，结果不能覆盖任何输入原件。优先保留未涉及的格式，结构不兼容时重新从原件复制、按步骤恢复处理并记录实际变化，不因合并、公式或重编号要求再次授权。默认只完成本次处理；只有用户明确说“保存流程”“以后每月按这个执行”等，才将公式、SQL、Python 或混合处理步骤保存为 Recipe 或更新已保存版本，下个月换个文件可一键重跑。生成结果文件与保存重复流程分别判断，执行中的自动修复不默认永久更新流程；脚本的实际代码、输入绑定、输出约定和校验随流程保存，重复执行直接运行已存代码；运行记录也保留代码与反馈，后续可查看并继续调整。
- **按客户记忆**：绑定客户后，普通聊天和表格处理都会在每轮读取客户名称、编号、说明和适用的长期记忆；同一客户的新旧对话共享已保存资料，更新后下一轮生效。普通聊天中提供的客户背景也可提取为长期参考，人工规则优先；不同客户与不同流程的业务规则分别隔离。没绑定的临时对话以后也能「保存到客户」。
- **异常反思与修复经验**：字段、表名、日期、类型或合并单元格等技术错误出现后，在下一轮执行中给出修复提示；正常任务不增加模型调用。修复经过实际执行和完成核对后，才按客户、流程保存少量技术经验供以后参考，可在「记忆与字段」查看或删除；业务规则仍以用户要求和人工记忆为准，Recipe 仍按用户的保存要求处理。
- **长任务上下文压缩**：自动将较早的完整工具交互整理成简短进度，收起旧 SQL、脚本参数和结果细节，保留用户要求、业务规则及最近步骤；原始参数、结果和执行状态仍可按证据分页回查。压缩在本地完成，不额外调用模型，也不会因未达到压缩目标停止任务。
- **对话管理流程**：可以直接说“删除某某流程”或“删除全部流程”。AI 列出当前客户或会话中的目标，只请用户确认一次，确认后由系统直接删除该流程及全部版本，不再由模型重复判断授权；表格文件和执行记录保留。
- **确认最终交付**：生成文件先作为候选，整轮收尾后确认正式交付清单；多次修正时核对适用版本，不把试算或被替代的文件并列展示。真正需要的多文件结果会一起保留，中间文件可在执行记录中追溯，默认输出列表只展示正式结果。

## 快速开始

```bash
./start.sh
```

Windows 双击项目根目录的 `start.bat`，或在终端运行：

```bat
start.bat
```

两个脚本执行相同流程：生成缺失的 `.env` → 强制结束占用后端端口（默认 `8000`，可通过 `PORT` 配置）和前端开发端口 `5173` 的进程 → 用已有的 `backend/.venv` 安装 `backend/requirements.txt` 中的依赖 → 安装、构建前端 → 启动后端。请提前准备好 `.venv`；如果缺少 pip，脚本会通过该环境的 `ensurepip` 补齐。端口空闲时直接继续；端口无法释放或安装、构建失败时停止并显示错误。每次启动都会检查两个端口，包括上次异常退出后留下的进程。

打开 <http://127.0.0.1:8000>，用 **admin / admin123** 登录。前端构建结果由后端统一提供页面，配置了其他 `PORT` 时使用启动日志中的地址。

配置模型：登录后到「设置」页，在 DeepSeek、千问或自定义 Tab 中填写 API Key、接口地址和模型名称，点「测试」确认后保存。接口地址和模型名称均可自行修改，DeepSeek 和千问提供默认接口地址。三项可以同时配置，互不覆盖；「启用」开关与「思考」同行，保存后生效。每次对话仅在已启用且配置完整的服务中，按 DeepSeek → 千问 → 自定义兼容服务的顺序选择。关闭服务会保留配置，全部关闭时没有可用模型；旧配置默认启用。自定义兼容服务适用于代理、网关和私有部署等 OpenAI Chat Completions 兼容接口。

设置页保存的 API Key、接口地址和模型会应用于所有会话的下一次对话，无需新建会话或重启。此前因未配置 Key 而失败的请求，可在原会话直接重新发送；历史报错保留供查看，不会作为模型的对话上下文。
完整 Key 由后端以明文 JSON 写入本机数据目录的 `settings.json`（默认 `backend/data/settings.json`，在支持 POSIX 权限的系统上设置为 `0600`）；设置页默认隐藏已保存 Key，点击眼睛图标后可查看。模型服务配置不再从 `.env` 或进程环境变量读取。

模型名称按原样保存并用于请求。千问及 DeepSeek 的 `deepseek-v4-pro`、`deepseek-flash` 提供「思考」开关（模型自身的推理能力，与输入框旁的「思考模式」不是一回事），默认关闭；保存后应用于后续请求。千问通过 OpenAI 兼容接口的 `enable_thinking` 参数控制思考，需使用支持切换思考模式的模型。

设置页的「高级配置」默认折叠，可按服务能力选择结构输出协议：自动兼容（默认）优先请求 JSON 模式，服务明确不支持时改用提示词；优先 JSON Schema 会在不支持时依次兼容 JSON 模式和提示词；仅提示词不发送结构输出参数。系统记住当前服务和模型明确不支持的协议，后续请求直接使用兼容方式，不为探测能力增加请求。结构化结果始终经过本地解析与校验，协议降级不会跳过检查。

意图、计划、核对结果及 Recipe 生成使用统一字段约定，错误反馈包含具体字段路径，并在同一份预算内修正 JSON、字段类型或输出引用。工具调用在显示和执行前整批校验；一批中任意调用格式不合格，该批全部暂缓，修正后再执行。协议纠错不计入业务失败，不触发换方法，也不生成一次虚假的流程执行记录。合法响应不会额外调用模型。明确不支持的协议缓存保留 30 分钟，并按服务地址、模型、凭据及思考开关等配置隔离；临时网络故障不会触发能力降级。

系统统一采用宽松兼容策略，适合私有部署和较弱模型。请求超时默认 1800 秒（范围 5–3600 秒），回复流连续无新内容默认等待 1800 秒，模型等待上限默认 3600 秒，工具执行默认等待 1800 秒；90 秒时只提示仍在等待。实际等待还受请求超时和主动开启的任务预算限制，任务预算默认关闭。高级配置中的「恢复默认等待与重试」可恢复对应默认值，点击保存后生效。ReAct 默认最多 200 轮，脚本任务额外预留 60 轮；普通模式最多 800 次工具调用，思考模式共享 1000 次。可通过 `.env` 的 `AGENT_MAX_ITERATIONS` 调整轮数，修改后需重启；继续已有任务时会采用提高后的轮数上限，并保留已经执行的进度和已用次数。用户可随时主动停止。

「上下文压缩」独立于任务预算，默认软字符目标为 80000，接近目标时开始整理旧过程；填写 0 则不按字符触发。私有模型可另填实际服务端上下文容量（Token），系统预留输出额度及安全余量后整理输入；默认 0 表示未指定，不按模型名称猜测。两个目标都为 0 时关闭软压缩，已主动开启的输入预算仍按原配置生效。短任务不改变；不能安全压缩的内容继续保留，最终禁止工具调用的轮次也保留原交互。

输出 Token 上限默认 8192（范围 1–131072），结构输出纠错默认 6 次（范围 0–10），工具调用纠错默认 12 次（范围 0–20），连接错误重试默认 3 次（范围 0–5），断流恢复默认 5 次（范围 0–10）。纠错或重试次数为 0 表示关闭对应重试；实际超时和输出上限还受模型服务限制。参数完整但缺少结束标志的工具调用可继续执行；不完整参数与尚未展示的截断响应可有限重试，不会直接当作完成；普通聊天已显示的半截正文会如实提示失败，避免重试后重复显示。API 的 `capabilities.structured_output` 保存协议选择；`stream_recovery_retries` 保存断流恢复次数，`sdk_retries` 保存连接重试次数；`structured_timeout` 默认 0（范围 0–900 秒，0 表示不额外限制整次结构化调用总时长）。单次请求超时沿用顶层 `timeout`。旧版设置中仍为原出厂默认的等待与重试会升级为宽松默认，自定义值及关闭重试的 `0` 保留。`runtime_policy.compatibility_mode` 仅保留为配置迁移标记，固定为 `relaxed`；旧值 `strict` 自动归一，同时保留已明确设置的等待和重试数值，保存后避免再次迁移。保存某一提供商或部分策略时会保留其他已有配置，包括 `false` 和 `0`。

不配置模型也能看效果：首次启动会写入一个示例客户「顺达物流（示例）」，里面有原始文件、人工结果样例、一个已验证的月结账单流程、字段映射和业务规则；客户页的「用新文件执行」不需要 AI。

环境要求：Python 3.10+、Node.js 20+，macOS / Linux 还需提供 `lsof`。Python 依赖统一维护在 `backend/requirements.txt`；启动脚本每次自动安装。需要手动安装时，Windows 用户在 `backend` 目录使用 PowerShell 执行：

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

在 `frontend` 目录执行 `npm install`、`npm run build`，再回到 `backend` 启动：

```powershell
.\.venv\Scripts\python.exe -m sheetmate
```

AI Python 脚本在所有平台固定使用 `backend/.venv`：Windows 为 `.venv\Scripts\python.exe`，macOS / Linux 为 `.venv/bin/python`。无需将 Python 加入系统 PATH；虚拟环境不存在时直接提示错误，不回退到系统 Python 或 Conda。

## 怎么用

1. **登录**，第一次会有三个小问题（岗位、常处理的表、想做什么）。
2. **客户页**：每个客户一张卡片（各有一个 IP 形象）。点开能看到：
   - **处理逻辑**：AI 写的「Excel 整体处理逻辑」说明（要处理的表 → 整体逻辑 → 执行步骤 → 交付结果 → 注意事项），旁边是主流程图。已保存流程有变化（明确要求保存/更新流程、保存到客户、编辑/删除）后会在后台自动重写；仅本次执行或自动修复不永久改流程。你手动编辑过就不再自动覆盖，点「重新总结」恢复。
   - **流程**：每个 Recipe 的流程图，每一步标明「内置公式 / 客户公式」「SQL」或「Python 脚本」，脚本详情可查看代码、输入输出绑定、校验与日志；输入要求、校验规则、版本历史；**用新文件执行**；最下面是「客户公式」（见下面第 5 点）。
   - **文件**：上传过的 Excel（含人工做好的结果样例）和每次生成的结果。
   - **运行记录**：在每个流程右上角的「处理详情」右侧查看该流程的执行记录，点开能看每一步的输入输出、中间表，**改参数后从某一步重跑**（复用前面算好的中间表）。
   - **记忆与字段**：业务规则、偏好，以及字段映射（标准字段 ← 各种表里的别名，例如 运单号 ← 单号）。
3. **新对话（首页）**：一句标题「你的专属表格 Agent 助手」 + 一个输入框，IP 形象挂在输入框右上角（选了客户就换成这个客户的形象）。首页和聊天页输入框均可通过「＋」、拖拽或复制粘贴添加 Excel/CSV 文件与 PNG/JPG/WebP/GIF 图片，支持直接粘贴截图；旁边有「思考模式」开关（默认关闭，见下文）。直接描述需求，不用选择分析、修改或建表。输入框下面是「选择客户」，点开选客户、新建客户或「不绑定客户」。
   - **图片附件**：添加后可预览原图，并随消息发送给支持图片输入的模型；可识别截图、解释图片或参考图片建表。每条消息最多 10 张图片，GIF/WebP 动图向模型发送首帧，上传原件不变；图片不会被误当成 Excel 工作表。使用不支持图片的模型时需在「设置」切换模型。
   - **直接建表**：例如「帮我建一个费用报销表，标题合并居中，下面有日期、项目、金额、备注，留十行，金额保留两位小数，最后加合计」。AI 自动整理字段、布局和格式，调用后台建表工具生成可下载的 `.xlsx`；也可以把已有文字明细粘贴进来一起建表。缺少真实数据时保持空白，有明显影响业务结果的歧义才会提问。
   - **脚本处理与持续调整**：复杂需求可由 AI 编写 Python，执行后读取实际错误、结果摘要、数据预览和核对记录，发现不符合要求就改脚本重试。用户对结果提出新意见时，AI 可以查看上一版脚本，继续生成新版。后台 AI 明确选择正式交付文件与需要展示的结果表；测试文件与草稿不进入正式下载列表；脚本中间数据在执行明细的“数据”页作为运行快照保留，代码与原始返回在“日志”中查看。每轮执行有超时和迭代次数限制，达到限制会如实说明未完成项；失败不会把已经写出的半成品当作成功文件交付。
   - 附件菜单里可以上传「**人工做好的结果**」：提出整理要求时，AI 会比对输入和结果，学出流程，并验证能不能复现你的结果。
   - **按需保存重复流程**：默认只处理当前任务，不自动把步骤加入每月重复执行的流程，也不主动询问是否保存。明确说“把刚才流程保存下来”或“以后每月都按这个处理”时，AI 才保存可复用流程；“保存表格”“导出 Excel”和临时修改已有流程都不代表永久保存规则。
   - 右侧「执行明细」按“流程、文件、数据、日志”排列：流程展示执行步骤与已保存流程；文件分输入、输出两组，各组按时间从早到晚排列；数据展示处理中间表、脚本运行快照与已展示的临时查询预览；日志支持按回答查看代码、SQL、JSON、完整参数与原始返回，提供搜索、错误筛选和复制。绑定客户后，流程、文件和数据汇集该客户全部会话及运行；日志仍按当前会话的回答定位。
   - **完成核对与停止记录**：模型停止输出后，处理任务会对照真实工具结果确认是否完成；仅返回“接下来执行”等进度说明时，在原有预算内最多补做十二次。完成核对沿用模型等待配置（默认 1800 秒），失败或超时会标明“尚未确认完成”。空响应、断流、输出上限、服务错误、执行轮数和操作次数耗尽都有明确原因，界面区分未完成、等待确认、失败和已停止。日志保留模型结束原因、耗时、剩余目标与最后执行步骤，执行中定期保存；服务重启后将未结束的记录标为中断，无法确认的具体原因标为未知。已有产出仍可查看，历史摘要只表示实际做过的操作，不代表全部任务完成。
   - **结构清晰的回复**：使用渲染后的 Markdown 小标题、列表和少量关键指标表格，区分结果、统计口径、异常与待确认事项。阶段回复与默认折叠的「思考细节：操作 · 对象」按发生顺序穿插展示，回复文字保留在对应位置，不收进折叠区；展开思考细节可查看该阶段的操作与计划状态。正文表格默认铺满可用宽度，按内容自动分配列宽，单元格之间显示分隔线；拖动表头右侧边缘调整列宽，双击恢复自适应，超宽内容在表内横向滚动。说明性小表最多 8 行数据、6 列、40 个数据单元格，且完整非空；正式明细和较大表格通过文件卡片预览、下载。回复聚焦任务内容和完成结果，不反复解释保留原格式、保护原件或另存文件等程序默认行为；用户询问或确有实际格式变化时才说明。右侧「执行明细」将正式文件、中间数据和开发者日志分别展示。
   - **普通模式与思考模式**：输入框旁的「思考模式」开关默认关闭，对应后端两种不同的 Agent 做法，**两种都不需要用户确认计划**。
     > 注意区分：这里的「思考模式」是 SheetMate 自己的 Agent 流程（多轮交互、计划与核对）；设置页里模型的「思考」开关是厂商模型自带的推理参数，两者互相独立，可以任意组合。
     - 普通模式（默认）：直接进入 ReAct 工具循环，速度快，适合日常的统计、查询、改表。
     - 思考模式：多花几次与大模型的交互换更高的准确度，适合金额口径复杂、数据脏、需要严谨核对的任务。后端的做法：
       1. **先看数据再规划**：规划前读取每张表真实的列类型、空值率、样本、候选主键和重复键（只读、不调用模型），规划时还能看到执行助手的完整工作环境（工具、客户资料、记忆、已有流程）。
       2. **起草计划**：写明对需求的理解、需求里没说清而采用的「默认口径」、数据里看得出的风险，以及每一项的**开场说明**和**验收标准**；同时由 AI 用 `show_plan` 决定向用户展示整体进度是否有帮助。
       3. **审查计划**：另起一次调用，对照需求和数据找遗漏、顺序错误、不存在的列、缺少勾稽核对的地方，有问题就采用修订版；独立复核 `show_plan`，无需修改步骤也能调整展示决定。
       4. **逐项执行并核对**：每一项仍是完整的 ReAct；做完后再起一次调用，只依据工具的真实返回判断是否达标，不达标就带着具体问题补做一次（最多一次，仍有问题则如实写出，不会无限重试）。
       5. **整理结论并核对回答**：最终回答先扣住，对照各项的工具结果检查数字和结论，发现与结果不符、凭空出现或声称已完成却没有产出的内容，就让智能体用工具核实并更正后再发出，错误回答不会展示给用户。
     - **给用户看的样子**：像同事边做边讲，而不是「第 N 步」的报告——
       - 开场白：对需求的理解、默认口径、数据里要留意的、计划审查的结果；
       - 每一项开始前一句话说现在要做什么（两项及以上），做完一两句汇报，紧跟一行核对结果（灰色引用，如「✓ 核对通过：去重后运单数 48，不大于明细行数 74」；核对发现问题会先说发现了什么、再补做，有问题的那次汇报不展示；核对没做成会写明原因）；
       - 过程中模型在忙、界面上没有别的变化时，聊天里有一行转圈的「此刻在做什么」（如「正在核对这一项的结果」），别的事情一发生就消失，不存库；
       - 最后是结论，回答下面有一行小字说明回答核对的结果（通过 / 发现出入并已更正 / 没能更正 / 没完成及原因）。
     - **由 AI 决定是否展示整体进度**：起草与审查计划时，根据展示对用户的价值返回 JSON 布尔值 `show_plan`，与步骤数量无关，不设固定步数阈值。多表依赖、多个交付、重要风险、明显耗时或需要跟踪的阶段可以展示，简单直接的任务可以隐藏；用户明确要求查看计划时展示。选择展示时，在输入框上方出现「任务进度」清单（进行中的一项转圈，做完一项打勾，做完自动收成一行，随时可点开），结论里也有「过程回顾」逐项交代；选择隐藏时，结论保持简洁。每项的开场和汇报仍按原有方式进行，只有一项时不复述需求、直接做。起草时缺失或非布尔的 `show_plan` 默认隐藏，审查时缺失或非布尔则保留起草决定；计划写不出来（兜底计划）时隐藏，开场白直接说明原因。事件继续使用兼容字段 `plan_start.checklist` 传递展示决定，最终过程回顾沿用同一决定。
     - **不出现编号标题**：提示词要求模型汇报时不写「第 N 步」「执行情况」「小结」；模型仍然写了的话，后端兜底去掉这类标题，只删标签、不改任何数字和结论。核对说明里的数字必须出现在工具的真实返回里，否则只说「核对通过」，不展示可能编造的数字；说明里带工具名或 SQL 的也不展示。
     - 需求里真正的业务歧义仍然通过执行中的 `ask_user` 提问；闲聊和查看文件不规划。工具调用预算为普通模式 80 次、思考模式 100 次，计划各项、补做和整理结论共用。所有辅助调用都有时限，按请求超时与模型等待上限放宽等待（默认 600 秒）。超时、调用失败或返回无法解析的内容时退回更简单的做法，不会让整次请求失败，也不会声称做过没做的核对。没完成的核对会写明原因（例如「模型 600 秒内没有返回」「模型服务限流」），同时在后端日志里留一行；某一项核对超时后，后面的核对不再逐个等，回答核对仍会试一次。没有调用过工具的项没有可核对的依据，不会为它多花一次模型调用；意图识别、核对、计划修复、记忆提取和客户摘要默认预留 4096 输出 Token，标题与文件说明预留 2048；默认关闭辅助思考，输出额度仍为可能计入的隐藏推理留出余量。结构化辅助调用不超过用户配置的输出上限，遇到明确截断时可在纠错次数内继续扩大额度。标题生成最多等待 60 秒，后台记忆提取最多等待 120 秒。
     - 对话页的开关是每个会话自己的状态，默认关闭；首页开着时，首条消息及该会话里的后续追问沿用。刷新页面后，历史消息仍标有「思考模式」，任务清单、各项汇报和核对行、回答核对的小标识都会按存下来的事件还原；计划审查、每项核对、回答核对的原始结果在右侧「执行明细」的开发者日志里。
     - 接口：`POST /api/conversations/{id}/chat` 的 `thinking: true`。原先「先出计划」的 `POST /api/conversations/{id}/plan` 确认式接口已移除；`plan_steps` 仍可由调用方直接传入，传入后跳过 AI 起草和审查，执行和核对照常进行；没有 AI 展示决定时默认不出任务清单和过程回顾。
   - **复制回复**：悬浮到助手消息时，底部显示「复制格式」和「复制 Markdown」，平时隐藏。前者复制带标题、列表、表格样式的富文本（粘贴目标需支持富文本），后者复制对应 Markdown 源文；包含阶段回复、最终回答及其中的 Markdown 表格和文件链接，不额外附加临时查询或中间计算表，不包含内部工具参数。完整表格通过文件卡片查看或下载。浏览器拒绝复制时明确提示失败。
   - **编辑输出沿用原格式副本**：原件始终只读，修改以保留原格式的工作簿副本为基础；读取和修改时都可按需生成分析副本，用公式、SQL 或脚本辅助分析、定位和计算，再由 Recipe 或脚本应用确认的修改，分析用的去格式化副本不能代替最终工作簿。优先保留标题、表头、列宽、数字格式、冻结窗格、单元格样式、批注和未涉及的 sheet；支持删行后修改序号等组合操作。结构兼容处理失败时重新复制原件并按步骤重做，实际需要调整的合并、格式或引用会随结果说明。汇总表作为新 sheet 追加；`.xlsm` 保持宏和扩展名。统计结果导出可以使用新的普通表格，不要求套用原表排版。
4. 临时对话里做出满意的结果后，点右上角「**保存到客户**」：选已有客户或新建客户，这次对话的文件、流程、记忆一起归到客户名下。
5. **客户公式**（客户详情页 →「流程」标签最下面）：内置公式覆盖不了的客户独有逻辑，用表单做成公式，流程里就能像内置公式一样调用。
   - **表单**：id、名称、用途、参数行（名称 / 类型 / 必填 / 说明 / 默认值）、SQL 模板。参数类型、默认值、模板里的 `{{参数}}` 是否都声明了、有没有错写在引号里，都是边写边校验；SQL 语法由后端实时检查（和保存时是同一套检查）。
   - **高级模式**：切到「JSON」直接改公式 JSON，格式有误时指出第几行，可一键定位。
   - **试运行**：编辑器右边的面板。选客户的某个文件（会按这个客户的字段映射统一列名）、粘贴从 Excel 复制的几行，或者用示例数据；参数输入框按声明的类型自动生成；点「运行」看结果预览和实际执行的 SQL。还没保存的公式也能试，试运行在临时工作区里完成，不会改动客户的任何数据。
   - 同一个 id 每保存一次升一个版本，流程总是用最新版本；被流程用到的公式不能停用，删除时列出受影响流程，用户确认一次后执行。列表里会标出被哪些流程用到，以及新版本让哪些流程的哪一步出了问题。id 和内置公式相同时，这个客户改用你写的版本（保存前会提醒）。

## 架构：三个来源，各管一层

```
                ┌──────────────────────── 前端 Vue 3（frontend/） ────────────────────────┐
                │ 登录/引导 · 客户卡片 · 客户详情 · 对话（ChatGPT/Qoder 布局）· 右侧执行明细 │
                └───────────────────────────────┬─────────────────────────────────────────┘
                                                │ HTTP + SSE（后台任务，刷新页面不中断）
┌───────────────────────────────────────────────┴───────────────────────────────────────────┐
│ api/  services/   FastAPI 接口 · 客户/会话/文件/流程/运行记录/记忆 · SQLite（data/app.db）  │
├──────────────────────────────────────────┬─────────────────────────────────────────────────┤
│ agent/      ← TabClaw 的 Agent 框架       │ recipe/     ← SheetAgent 的核心逻辑            │
│ ReAct 工具循环（流式、分片拼接、DeepSeek  │ 输入 vs 输出四层 diff（+长转宽/匹配/填充值） │
│ 标记清理）、计划执行 + 自检、澄清、多表   │ Recipe 结构、按步执行、运行校验、与人工结果  │
│ 并行专员 + 汇总、记忆、工作流记录、压缩   │ 比对（信任闸门）、学习/修正/修订             │
├──────────────────────────────────────────┴─────────────────────────────────────────────────┤
│ engine/     ← SheetMate 的引擎闭环                                                          │
│ 读取（表头探测/合并单元格/多行表头）→ 画像 → 公式 / SQL / Python（可混合）                   │
│ → DuckDB / 脚本沙箱 → 业务校验 → 出错内层修复 → 写回新 Excel（源文件只读）                   │
└─────────────────────────────────────────────────────────────────────────────────────────────┘
```

**谁负责什么**：AI 负责「想」（理解需求、选择公式/SQL/脚本、规划步骤、出错时修复），引擎负责「做」：内置公式编译成 DuckDB SQL，声明式建表规范交给工作簿模块，Python 脚本交给独立的受限子进程执行。

建表能力通过 `create_workbook` 工具独立封装，沿用同一套后台 Agent 和文件交付链路：文字或已读取的资料 → AI 整理二维网格、合并范围和样式 → 结构校验 → 工作簿写入 → 文件登记与下载。这个工具接收结构化 JSON；普通字符串按文本保存，只有明确的 `{ "formula": "=SUM(C3:C12)" }` 单元格才作为 Excel 公式写入，公式在 Excel 等软件打开时重算；`{ "date": "2026-10-31" }` 写入真正的 Excel 日期。合并范围重叠、合并会覆盖已有内容、坐标越界或样式无效时，工具返回具体错误供 AI 修正。生成文件后可以继续分析或做数据修改；对标题、配色、合并等建表排版的追问，通过 `inspect_workbook_creation` 读取已保存布局，按 `base_file_id` 继续调整，保留未修改的数据、公式及其他工作表。默认更新当前结果，明确要求独立副本或保留旧版时新增文件。也可选择 Python 创建复杂工作簿。没有实际文件交付时，最终回复会明确说明尚未生成工作簿。

脚本能力通过 `run_python_script` 独立封装，与分析/修改/建表模式组合使用，不增加前端模式开关。脚本可以读取选定的 `tables` 数据副本和 `files` 工作簿副本，使用 pandas、NumPy、openpyxl 等已安装库。`result_tables` 中的 DataFrame 可继续用公式或 SQL，默认供 AI 内部处理；只有 `display_tables` 明确列出的正式结果表才向用户展示。`OUTPUT_DIR` 中写入文件不代表自动交付，AI 用 `deliver_files` 选定最终文件，例如 `deliver_files = [OUTPUT_DIR / "武汉行程.xlsx"]`，通过检查后才登记为可下载文件。两个名单默认均为空；`probe.xlsx` 等测试文件、草稿和调试表不进入文件列表、右侧数据或回复，临时目录中的辅助文件执行结束后清理。`result` 和 `check(条件, 说明)` 提供内部摘要与核对依据。失败会把错误交回 AI，由它决定修改代码、调整方法或澄清业务口径；`inspect_python_script` 可读取有权限的历史脚本及输入说明，支持下一轮继续调整。脚本运行记录可查看并继续调整，成功脚本也可保存为 Recipe 步骤，与公式、SQL 混合重复执行；保存实际代码、表和文件绑定、输出与校验，无需 AI 重写。

| 来源 | 借鉴了什么 | 改成了什么 |
|---|---|---|
| [TabClaw](https://github.com/ustc-table-mining/TabClaw) | 整体 Agent 框架：ReAct 循环、计划模式 + 自检、澄清、多表并行 + 汇总、四类记忆、工作流记录、历史压缩、SSE | 前端全部重写为 Vue；pandas 内存表换成 DuckDB 工作区（重启不丢）；工具从 pandas 技能换成「公式」；修了多表并行误传结果表的问题；对话作为后台任务运行 |
| [SheetAgent](https://github.com/hvithalani/sheetagent)（MIT） | 输入 vs 输出的结构化 diff、Recipe 结构（inputs / steps / output_spec / validation_rules / learned_from / metadata）、执行器、运行校验、与人工结果比对 | 去掉 M 语言，步骤统一为「工具类型 + 参数」；支持公式、SQL 与受限 Python 脚本；比对按主键对齐行、通过线收紧到 98%；diff 补充长转宽、宽转长、跨表匹配、填充值检测；修正时保留效果最好的一轮 |
| SheetMate 设计方案（`docs/`） | 指令三层（原语 → 公式 → 配方）、scope 与覆盖、参数声明 vs 取值、字段别名映射、外层计划 + 内层 ReAct 修复、校验断言、有界重试 + 人话错误报告、单步运行与断点续跑、版本与状态 | 原样实现在 `engine/` 和 `recipe/executor.py` |

### 修改模式的闭环（`recipe/pipeline.py`）

```
处理说明 + 输入表 + 人工结果
  → 按需在独立分析副本中查看、筛选、计算或生成中间表，保留来源和原表定位信息
  → diff 找证据（例：「费用类型」的取值变成了列；合计 = 运费 + 保价费 + 包装费；「新食研」不在归属表里 → 匹配不到时的填充值）
  → LLM 结合输入画像规划 Recipe（公式、SQL、Python 或混合步骤）→ 结构检查（不过就让 LLM 改）
  → 逐步执行：公式 / SQL 交给 DuckDB，Python 交给脚本沙箱；断言不过或报错 → 内层 ReAct 修复（最多 3 次，只修技术层）→ 超限出人话错误报告
  → 运行校验 + 与人工结果比对：不一致就带着差异明细让 LLM 修正，最多 2 轮，取最好的一轮
  → 将修改应用到独立的原格式工作簿副本，输出新 Excel；只有用户明确要求才保存 Recipe，保存后即可复用
```

用户在对话里提修改意见时走 `revise_recipe`：基于已有步骤完成本次处理，只有明确要求更新重复流程时才保存新版本；和原人工样例的对比只作参考，不会把用户有意改的规则「修正」回去。

## 对话日志

默认写入 `backend/data/log/<对话ID>.log`；设置 `SHEETMATE_DATA_DIR` 后写入对应数据目录的 `log/`。每个对话一个 UTF-8 文件，持续追加后续轮次。用户的一次请求及其 AI 回复为一个 `TURN BEGIN / TURN END` 区块，区块之间用四个空行分隔。每条记录只有两行：时间戳、事件和函数路径一行，紧凑 JSON 数据一行。

日志保留以下数据节点：

- `chat.input`：前端提交的 body，一轮仅记一次；保留显式空值、额外字段及业务原值。非法 JSON 保留原文，并记录拒绝原因。
- `llm.request / llm.response`：每次模型调用各一条完整请求、完整响应；流式正文、思考和工具参数先聚合，不逐 token 写日志。保留实际模型消息、工具定义、用量、结束原因和耗时，失败或取消也保留已收到的数据。
- `tool.input / tool.result`：每次工具调用的完整参数、完整结果和实际实现函数；流式返回的文件、流程保存等业务产物合并到结果记录中。未执行、参数拒绝、复用和阻断均标明状态与原因。
- `chat.output / turn.end`：完整最终回复、展示的文件等业务产物、执行状态和停止原因；只写最终结果，不重复持久化检查点或整份前端事件数组。非空的记忆保存结果另记一条。

HTTP 请求头、方法、查询串、SSE 镜像、函数进出、重复上下文和重复工具反馈不再记录，异常仅保留类型、错误码与原因。后台任务归入触发它们的原轮次，即使下一轮已经开始也不会混写到下一轮。`turn.end` 表示本轮业务已结束；结构性的 `TURN END` 用于区分区块。服务重启时会给已保存的未结束执行补充中断原因。认证字段脱敏，业务数据不按界面展示限制截断。日志写入失败会报告到服务标准日志，聊天仍继续。旧日志文件不会自动清理或改写。

  "scope": "customer", "customer_id": "c_xxx",

Recipe 每一步明确记录 `kind=formula|sql|python`。公式保存公式 id 与参数，SQL 用 `custom_sql` 保存一条 DuckDB SELECT；Python 用 `python_script` 保存脚本文件引用、输入表、文件绑定和输出表映射，执行时从脚本文件读取实际代码并进入同一受限环境。三类步骤可任意混合，脚本结果表可继续交给公式或 SQL，后续脚本可引用前一步文件。流程输入区分数据表与完整文件，纯排版脚本无需虚构数据表；旧流程会自动推断工具类型，继续兼容执行。

Python 源码独立保存在 `data/scripts/scr_<UUID>.py`，每个脚本版本都有唯一 ID 和最多 20 个字符的标题。运行记录、流程节点和消息日志只保留 `script_id`、`script_title`、`script_filename` 等引用，不重复嵌入完整源码。点击节点、执行时间线或日志中的脚本文件可按需查看、复制和下载；修改代码会生成新 ID，历史版本仍可查看和重跑。旧记录中的内嵌代码在读取时自动迁移为文件引用，查看和重跑均沿用原会话或客户的权限。

### 内置公式（`engine/formulas/builtin.py`）

| 类别 | 公式 |
|---|---|
| 清洗整理 | `select_columns` 选择列 · `drop_columns` 删除列 · `rename_columns` 改名 · `filter_rows` 筛选 · `drop_duplicates` 去重 · `sort_rows` 排序 · `fill_null` 填空值/向下填充 · `trim_text` 清理空格 · `cast_columns` 转类型 |
| 计算 | `compute_column` 计算列 · `map_values` 值映射 · `split_column` 拆分列 · `concat_columns` 合并列 · `add_serial` 序号 |
| 匹配合并 | `lookup` 匹配带出列（键标准化、重复键检测/拦截、匹配率、匹配不到填充、可选模糊匹配） · `join_tables` 两表合并（一对多告警） · `concat_tables` 纵向合并 |
| 汇总统计 | `group_aggregate` 分组汇总 · `top_n` 取前 N · `append_total` 合计行 |
| 结构重塑 | `pivot_wide` 长转宽（一单多行 → 一单一行） · `unpivot_long` 宽转长 |
| 自定义 | `custom_sql` 一条 DuckDB SELECT |

新增能力 = 新增一个公式（内置：在 `builtin.py` 注册；客户独有：在客户页的「客户公式」里用表单做，或者 `POST /api/customers/{id}/formulas` 提交 SQL 模板，`{{参数}}` 占位，同 id 覆盖内置），不用改引擎。

客户公式相关接口（都要有这个客户的权限）：`GET /api/customers/{id}/formulas`（每个公式只有最新版本，带使用情况）· `POST …/formulas`（保存，升一个版本）· `POST …/formulas/check`（只检查不保存）· `POST …/formulas/trial`（试运行：`formula` + `params` + `inputs`，数据来自客户的文件或粘贴文本；失败也返回 200，看 `result.status` / `result.stage`）· `PUT …/formulas/{fid}/status`（启用 / 停用）· `DELETE …/formulas/{fid}`。保存时的定义检查在 `engine/formulas/base.py` 的 `Formula.check_definition`：参数名、枚举可选值、`column` 所属的表、默认值类型、占位符都声明了且没写在引号里、参数用示例值代入后是一条合法的 SELECT、id 不和系统工具重名。试运行超过 20 秒会自动中止。

## 安全与数据

- 所有数据（SQLite、上传文件、输出文件、DuckDB 工作区）都在 `backend/data/`，唯一的外部连接是你配置的模型接口。
- 源文件只读。继续修正、补充或重新生成同一结果时，新结果成功生成并确认交付后更新当前结果列表；旧版本留在执行记录中供追溯。明确另做一份、保留版本或处理不同任务/批次时新增文件，失败或停止时保留原结果。
- 客户和会话通过独立引用共用同一份文件原件及文件 ID。删除会话后客户文件保留；从客户移除文件或删除客户后，现存会话仍可下载、加载和继续处理这些文件，新会话不再继承已移除的客户文件。会话改绑客户时，新旧客户分别保留引用。解除最后一个引用后才回收原件。启动时自动创建客户/会话文件引用表，兼容已有文件记录；旧版本已物理删除的原件需重新上传。
- 上传、独立生成结果或绑定客户时，同一可见范围内的重名文件会在扩展名前依次加上 `（1）`、`（2）`，例如 `账单（1）.xlsx`；更新同一结果后旧版本不再占用当前名称，避免反复修订累积编号。独立客户可以使用相同文件名。文件 ID 和脚本内部文件引用不随展示名变化。
- DuckDB 连接一打开就关闭外部访问并锁定配置：SQL 读不了本机文件、连不了网、装不了扩展；用户和 AI 写的 SQL 只允许单条 SELECT；列名表名一律转义。
- Python 脚本固定由 `backend/.venv` 的解释器在独立子进程与临时目录执行，只传入选定的表和工作簿副本，运行环境不继承 API Key 等宿主凭据。macOS 使用 `sandbox-exec`、Linux 使用 `bwrap` 限制文件访问和网络，隔离设施不可用时返回明确错误；Windows 使用普通子进程，不提供操作系统级文件或网络隔离。各平台均保留执行超时、取消和结果大小限制，Windows 停止时通过 `taskkill` 结束进程树。正常完成、失败或停止后清理临时文件，只有显式列入 `deliver_files` 且通过输出检查的正式文件进入下载列表，临时测试文件不会登记为用户文件；脚本返回的内部数据表单独保存为运行快照，供执行明细排查。
- 登录令牌是签名的 httpOnly Cookie；成员只能看到自己创建或被分配的客户，管理员能看到全部。
- AI 回复过程中切换页面或刷新，回到会话会补齐已生成的回复和执行进度，并继续实时接收后续内容；网络中断后会自动重连。
- API Key 按服务商分别保存在 `backend/data/settings.json`（本机明文），页面默认隐藏，可点击眼睛图标查看。

## 用真实 DeepSeek 实测过的场景

| 场景 | 结果 | 耗时 |

| （已替换为思考模式的旧功能）确认式计划：先拆 7 步计划，确认后按步执行 + 自检 | 每一步真的调用工具完成，最后导出 Excel | 约 20 秒 |

| 下个月出现新的费用类型「偏远费」 | 流程标记失败，说清是哪个新类别、几行、少了多少钱（84.00），文件仍可下载核对；一句话修订后 v2 通过，合计与输入一致 | 约 30 秒 |

实测中发现并修复的问题：修改模式下模型反复核对同一数据把推理轮数耗光（允许必要的辅助分析和核对，有足够依据后提醒它交给 Recipe 完成修改与交付，且最后一轮强制作答）；校验规则参数名写法不统一导致误报「合计对不上」（现在多种写法都认，写错时明确报「规则写错了」）；流程先筛选后汇总时合计校验对不上（新增 `input_filter`）；两张输出表之间对账（新增输出 sheet 作为对比来源）；计划模式只把文字结论带到下一步，导致模型「说了但没做」（现在带上真实的工具调用记录）；同时上传 9 月、10 月两张明细时表名冲突、同类表被拆给多个专员导致无法对比；浮点尾数（341.73999999999995）出现在预览和 Excel 里。

## 已知限制 / 下一步

- 新建工作簿可以直接使用对话中的文字和已读取的表格资料；当前附件入口只读取 Excel / CSV，尚未新增音频转写、图片 OCR 或 PDF / Word 内容解析。口述需求需要先转成文字输入。
- 没有管理员给成员分配客户的界面（数据模型和权限检查已经支持，`user_customers` 表）。
- 客户公式只有「新建 / 保存新版本」，界面上没有看旧版本、回退旧版本的入口（旧版本都保留在库里）；试运行的数据只能是客户的文件或粘贴的几行，不能用别的流程的中间表。
- AI 优先选择内置公式或 SQL，只有它们不好做或超出能力范围时才用 Python，可按稳定性、性能和准确性组合使用；三类步骤均可保存并直接重复执行。客户公式目前由人在表单里维护，AI 不会自己创建。
- 编辑输出依赖 openpyxl，并非支持所有 Excel 特性。修改始终基于原格式工作簿的独立副本，优先精确修改；遇到结构不兼容时重新加载干净副本进行兼容处理，并将实际格式或引用变化写入输出提示。控件、切片器、嵌入对象等扩展特性仍可能变化，不承诺所有 Excel 特性都能原样保留；文件损坏、无法读取或业务校验失败仍会如实报告。旧版 `.xls` 编辑需要先另存为 `.xlsx`；CSV 没有工作簿格式，可生成普通结果表。原件不会被覆盖，分析副本可去格式化但不用于替代修改交付；程序异常退出或进程被强制终止不在正常临时文件清理保证范围内。
- 读取 Excel 同时检查公式与缓存：无缓存、Excel 错误和读取截断会记录质量风险并阻止把不可靠值作为完整统计依据；当前没有内置 Excel 公式重算服务。
- 单机本地部署设计（SQLite + 进程内后台任务），多人大并发时需要换 PostgreSQL 和任务队列，接口不用变。
