# SheetMate · 通用 Excel Agent

会**分析**、会**改表**、会把改表过程**记成流程（Recipe）每月重复执行**的 Excel 助手。本地部署，数据只在你的电脑上，只要配置一个 DeepSeek API Key 就能用。

- **自动理解需求**：不用选择「分析 / 修改」，后端 AI 每轮结合当前要求和上下文自动判断。
- **统计查询**：先复制原文件和数据到独立临时工作区，再按分析需要筛选、转换或计算，不限制临时副本的排版；结束、失败或停止后清理临时副本，原文件、已展示的结果表和明确导出的结果保留。
- **编辑表格**：同样先复制原始文件，读取、执行和写回都使用副本，重复执行和断点重跑也遵守这一规则；只修改要求的内容，保留原有格式，结果不能覆盖任何输入原件。处理过程做成 Recipe：一步步「公式 + 参数」，下个月换个文件一键重跑，正常执行不再调用 AI。
- **按客户记忆**：对话可以绑定客户，按客户的处理逻辑、流程、业务规则、字段映射来聊；没绑定的临时对话以后也能「保存到客户」。

## 快速开始

```bash
./start.sh
```

第一次运行会自动：生成 `.env` → 建 Python 虚拟环境并安装依赖 → 安装并构建前端 → 启动服务。然后打开 <http://127.0.0.1:8000>，用 **admin / admin123** 登录。

配置模型（二选一）：

- 在 `.env` 里填 `DEEPSEEK_API_KEY=sk-...`，重启；
- 或者登录后到「设置」页填 API Key，点「测试连接」，保存后立即生效（也可以换成硅基流动、阿里云百炼等 OpenAI 兼容服务）。

不配置模型也能看效果：首次启动会写入一个示例客户「顺达物流（示例）」，里面有原始文件、人工结果样例、一个已验证的月结账单流程、字段映射和业务规则；客户页的「用新文件执行」不需要 AI。

环境要求：Python 3.10+、Node.js 20+。Windows 用户在 `backend` 目录执行 `python -m venv .venv`、`.venv\Scripts\pip install -r requirements.txt`，在 `frontend` 目录执行 `npm install && npm run build`，再回到 `backend` 执行 `.venv\Scripts\python -m sheetmate`。

开发模式（前端热更新）：`./dev.sh`，打开 <http://localhost:5173>。

## 怎么用

1. **登录**，第一次会有三个小问题（岗位、常处理的表、想做什么）。
2. **客户页**：每个客户一张卡片（各有一个 IP 形象）。点开能看到：
   - **处理逻辑**：AI 写的「Excel 整体处理逻辑」说明（要处理的表 → 整体逻辑 → 执行步骤 → 交付结果 → 注意事项），旁边是主流程图。流程有变化（对话里生成/修订、保存到客户、执行时自动修复、编辑/停用/删除）后会在后台自动重写；你手动编辑过就不再自动覆盖，点「重新总结」恢复。
   - **流程**：每个 Recipe 的流程图，每一步标明是「内置公式」还是「客户独有」；输入要求、校验规则、版本历史、启用/停用；**用新文件执行**；最下面是「客户公式」（见下面第 5 点）。
   - **文件**：上传过的 Excel（含人工做好的结果样例）和每次生成的结果。
   - **运行记录**：每次执行的明细，点开能看每一步的输入输出、中间表，**改参数后从某一步重跑**（复用前面算好的中间表）。
   - **记忆与字段**：业务规则、偏好，以及字段映射（标准字段 ← 各种表里的别名，例如 运单号 ← 单号）。
3. **新对话（首页）**：一句标题「你的专属表格 Agent 助手」 + 一个输入框，IP 形象挂在输入框右上角（选了客户就换成这个客户的形象）。输入框左下角「＋」上传表格（也可以直接把文件拖进来），旁边可选「先出计划」；直接描述需求，不用选择分析或修改。输入框下面是「选择客户」，点开选客户、新建客户或「不绑定客户」。
   - 附件菜单里可以上传「**人工做好的结果**」：提出整理要求时，AI 会比对输入和结果，学出流程，并验证能不能复现你的结果。
   - 右侧「执行明细」：过程（每一步状态、工具调用参数和结果）、数据（工作区里的表，可以把某张表标记为期望结果）、文件、流程。
   - **结构清晰的回复**：使用渲染后的 Markdown 小标题、列表和关键指标表格，区分结果、统计口径、异常与待确认事项。选择「先出计划」后，消息逐步展示每一步的名称、状态和执行摘要；失败、待确认、已停止和未执行不会冒充完成。普通任务执行时显示最新进展，结束后过程说明收进默认折叠的「执行过程」，不再把每段过程与最终答案重复平铺。一条回答里展示最后一张结果表，其他中间表在右侧「执行明细」中查看。
   - **复制回复**：每条助手回复底部有「复制格式」和「复制 Markdown」。前者复制带标题、列表、表格样式的富文本（粘贴目标需支持富文本），后者复制对应 Markdown 源文；包含计划摘要、当前结果表预览和文件链接，不包含内部工具参数。预览不完整时会标明只复制了部分行，完整数据仍需下载或查看全部。浏览器拒绝复制时明确提示失败。
   - **编辑输出保留原格式**：在原工作簿的副本中修改，保持标题、表头、列宽、数字格式、冻结窗格和未涉及的 sheet；同布局修改只更新变化的单元格，保留原单元格样式、批注、超链接、合并结构及未修改的公式。汇总表作为新 sheet 追加；`.xlsm` 保持宏和扩展名。涉及不能安全保留的复杂结构时停止并说明原因，不生成丢格式的替代文件。统计结果导出可以使用新的普通表格，不要求套用原表排版。
4. 临时对话里做出满意的结果后，点右上角「**保存到客户**」：选已有客户或新建客户，这次对话的文件、流程、记忆一起归到客户名下。
5. **客户公式**（客户详情页 →「流程」标签最下面）：内置公式覆盖不了的客户独有逻辑，用表单做成公式，流程里就能像内置公式一样调用。
   - **表单**：id、名称、用途、参数行（名称 / 类型 / 必填 / 说明 / 默认值）、SQL 模板。参数类型、默认值、模板里的 `{{参数}}` 是否都声明了、有没有错写在引号里，都是边写边校验；SQL 语法由后端实时检查（和保存时是同一套检查）。
   - **高级模式**：切到「JSON」直接改公式 JSON，格式有误时指出第几行，可一键定位。
   - **试运行**：编辑器右边的面板。选客户的某个文件（会按这个客户的字段映射统一列名）、粘贴从 Excel 复制的几行，或者用示例数据；参数输入框按声明的类型自动生成；点「运行」看结果预览和实际执行的 SQL。还没保存的公式也能试，试运行在临时工作区里完成，不会改动客户的任何数据。
   - 同一个 id 每保存一次升一个版本，流程总是用最新版本；被流程用到的公式不能停用 / 删除，列表里会标出被哪些流程用到，以及新版本让哪些流程的哪一步出了问题。id 和内置公式相同时，这个客户改用你写的版本（保存前会提醒）。

## 架构：三个来源，各管一层

```
                ┌──────────────────────── 前端 Vue 3（frontend/） ────────────────────────┐
                │ 登录/引导 · 客户卡片 · 客户详情 · 对话（ChatGPT/Qoder 布局）· 右侧执行明细 │
                └───────────────────────────────┬─────────────────────────────────────────┘
                                                │ HTTP + SSE（后台任务，刷新页面不中断）
┌───────────────────────────────────────────────┴───────────────────────────────────────────┐
│ api/  services/   FastAPI 接口 · 客户/会话/文件/流程/运行记录/记忆 · SQLite（data/app.db）  │
├──────────────────────────────────────────┬─────────────────────────────────────────────────┤
│ agent/      ← TabClaw 的 Agent 框架       │ recipe/     ← SheetAgent 的核心逻辑            │
│ ReAct 工具循环（流式、分片拼接、DeepSeek  │ 输入 vs 输出四层 diff（+长转宽/匹配/填充值） │
│ 标记清理）、计划执行 + 自检、澄清、多表   │ Recipe 结构、按步执行、运行校验、与人工结果  │
│ 并行专员 + 汇总、记忆、工作流记录、压缩   │ 比对（信任闸门）、学习/修正/修订             │
├──────────────────────────────────────────┴─────────────────────────────────────────────────┤
│ engine/     ← SheetMate 的引擎闭环                                                          │
│ 读取（表头探测/合并单元格/多行表头）→ 画像 → 字段标准化 → 公式（参数声明 + SQL）            │
│ → DuckDB 执行（沙箱）→ 断言 → 出错内层修复 → 写回新 Excel（源文件只读）                     │
└─────────────────────────────────────────────────────────────────────────────────────────────┘
```

**谁负责什么**：AI 负责「想」（理解需求、选工具、规划步骤、出错时修复），引擎负责「做」（每一步都编译成 DuckDB SQL 确定性执行）。

| 来源 | 借鉴了什么 | 改成了什么 |
|---|---|---|
| [TabClaw](https://github.com/ustc-table-mining/TabClaw) | 整体 Agent 框架：ReAct 循环、计划模式 + 自检、澄清、多表并行 + 汇总、四类记忆、工作流记录、历史压缩、SSE | 前端全部重写为 Vue；pandas 内存表换成 DuckDB 工作区（重启不丢）；工具从 pandas 技能换成「公式」；修了多表并行误传结果表的问题；对话作为后台任务运行 |
| [SheetAgent](https://github.com/hvithalani/sheetagent)（MIT） | 输入 vs 输出的结构化 diff、Recipe 结构（inputs / steps / output_spec / validation_rules / learned_from / metadata）、执行器、运行校验、与人工结果比对 | **去掉 M 语言和 pandas 代码**，步骤改为「公式 + 参数」；比对按主键对齐行、通过线收紧到 98%；diff 补充长转宽、宽转长、跨表匹配、填充值检测；修正时保留效果最好的一轮 |
| SheetMate 设计方案（`docs/`） | 指令三层（原语 → 公式 → 配方）、scope 与覆盖、参数声明 vs 取值、字段别名映射、外层计划 + 内层 ReAct 修复、校验断言、有界重试 + 人话错误报告、单步运行与断点续跑、版本与状态 | 原样实现在 `engine/` 和 `recipe/executor.py` |

### 修改模式的闭环（`recipe/pipeline.py`）

```
处理说明 + 输入表 + 人工结果
  → diff 找证据（例：「费用类型」的取值变成了列；合计 = 运费 + 保价费 + 包装费；「新食研」不在归属表里 → 匹配不到时的填充值）
  → LLM 用公式目录规划 Recipe（只填参数，不写代码）→ 结构检查（不过就让 LLM 改）
  → 逐步执行：公式 → SQL → DuckDB；断言不过或报错 → 内层 ReAct 修复（最多 3 次，只修技术层）→ 超限出人话错误报告
  → 运行校验 + 与人工结果比对：不一致就带着差异明细让 LLM 修正，最多 2 轮，取最好的一轮
  → 输出新 Excel、保存 Recipe（复现人工结果 → 已启用；否则草稿）
```

用户在对话里提修改意见时走 `revise_recipe`：生成新版本；和原人工样例的对比只作参考，不会把用户有意改的规则「修正」回去。

## Recipe 长什么样

```jsonc
{
  "id": "rcp_xxx", "version": 2, "name": "月结账单整理", "status": "active",
  "scope": "customer", "customer_id": "c_xxx",
  "inputs": [{
    "alias": "运费明细", "file_pattern": "运费明细*", "sheet": "明细",
    "expected_columns": ["运单号", "下单日期", "店铺名称", "费用类型", "金额", "重量(kg)"],
    "required_columns": ["运单号", "店铺名称", "费用类型", "金额"],   // 步骤实际用到的列
    "key_columns": ["运单号"], "column_matching": "fuzzy",
    "expected_row_range": [20, 400], "header": {"header_row": 2, "header_rows": 1}
  }],
  "field_mapping": {"运单号": ["单号"], "店铺名称": ["店铺"]},
  "steps": [{
    "id": 1, "name": "费用拆成列", "formula": "pivot_wide", "formula_kind": "builtin",
    "params": {"table": "运费明细", "index": ["运单号"], "pivot_column": "费用类型", "value_column": "金额",
               "values": ["运费", "保价费", "包装费"], "fill_value": 0, "carry_columns": ["下单日期", "店铺名称"]},
    "output": "运单费用",
    "description": "每个运单一行，运费、保价费、包装费各一列",      // 给人看
```

每一步只存「公式 + 参数」，执行时由引擎编译成 SQL：AI 不会写出不可控的代码；客户独有、内置公式表达不了的逻辑用 `custom_sql`（一条 SELECT，同样在沙箱里执行），界面上标为「客户独有」。

### 内置公式（`engine/formulas/builtin.py`）

| 类别 | 公式 |
|---|---|
| 清洗整理 | `select_columns` 选择列 · `drop_columns` 删除列 · `rename_columns` 改名 · `filter_rows` 筛选 · `drop_duplicates` 去重 · `sort_rows` 排序 · `fill_null` 填空值/向下填充 · `trim_text` 清理空格 · `cast_columns` 转类型 |
| 计算 | `compute_column` 计算列 · `map_values` 值映射 · `split_column` 拆分列 · `concat_columns` 合并列 · `add_serial` 序号 |
| 匹配合并 | `lookup` 匹配带出列（键标准化、重复键检测/拦截、匹配率、匹配不到填充、可选模糊匹配） · `join_tables` 两表合并（一对多告警） · `concat_tables` 纵向合并 |
| 汇总统计 | `group_aggregate` 分组汇总 · `top_n` 取前 N · `append_total` 合计行 |
| 结构重塑 | `pivot_wide` 长转宽（一单多行 → 一单一行） · `unpivot_long` 宽转长 |
| 自定义 | `custom_sql` 一条 DuckDB SELECT |

新增能力 = 新增一个公式（内置：在 `builtin.py` 注册；客户独有：在客户页的「客户公式」里用表单做，或者 `POST /api/customers/{id}/formulas` 提交 SQL 模板，`{{参数}}` 占位，同 id 覆盖内置），不用改引擎。

客户公式相关接口（都要有这个客户的权限）：`GET /api/customers/{id}/formulas`（每个公式只有最新版本，带使用情况）· `POST …/formulas`（保存，升一个版本）· `POST …/formulas/check`（只检查不保存）· `POST …/formulas/trial`（试运行：`formula` + `params` + `inputs`，数据来自客户的文件或粘贴文本；失败也返回 200，看 `result.status` / `result.stage`）· `PUT …/formulas/{fid}/status`（启用 / 停用）· `DELETE …/formulas/{fid}`。保存时的定义检查在 `engine/formulas/base.py` 的 `Formula.check_definition`：参数名、枚举可选值、`column` 所属的表、默认值类型、占位符都声明了且没写在引号里、参数用示例值代入后是一条合法的 SELECT、id 不和系统工具重名。试运行超过 20 秒会自动中止。

## 安全与数据

- 所有数据（SQLite、上传文件、输出文件、DuckDB 工作区）都在 `backend/data/`，唯一的外部连接是你配置的模型接口。
- 源文件只读，结果永远写成新文件。
- DuckDB 连接一打开就关闭外部访问并锁定配置：SQL 读不了本机文件、连不了网、装不了扩展；用户和 AI 写的 SQL 只允许单条 SELECT；列名表名一律转义。
- 登录令牌是签名的 httpOnly Cookie；成员只能看到自己创建或被分配的客户，管理员能看到全部。
- API Key 保存在 `backend/data/settings.json`（本机明文，页面上只显示首尾几位）。

## 用真实 DeepSeek（deepseek-chat）实测过的场景

| 场景 | 结果 | 耗时 |
|---|---|---|
| 分析：按店铺统计运费合计和票数，再追问保价费占比 | 数字与原表一致，主动提示一单多行要按运单号去重 | 3~5 秒 |
| 修改：上传原始表 + 人工结果，「照着人工结果整理，每月都要做」 | 生成 8 步流程，与人工结果逐格 100% 一致，直接启用 | 约 40 秒 |
| 修订：「归属汇总里加一列运费合计，只算运费」 | 生成 v2，新列出现在 Excel 里，其余结果不变 | 约 20 秒 |
| 复用：绑定客户，用已有流程处理 10 月新文件（列名变成「单号/店铺」） | 字段映射自动统一列名，不调用 AI 生成，直接出结果 | 约 6 秒 |
| 对比两个月的明细，找运费变化最大的店铺 | 跨表 JOIN 算出每店变化，并拆解原因（单量 vs 单均重量） | 约 25 秒 |
| 计划模式：先拆 7 步计划，确认后按步执行 + 自检 | 每一步真的调用工具完成，最后导出 Excel | 约 20 秒 |
| 脏数据：表头在第 3 行、有取消/退款订单、金额是带千分位的文本、客户名带空格，只给人工结果 | 自动识别表头、推断出「只算已完成」和「匹配不到记普通」，与人工结果 100% 一致 | 约 20 秒 |
| 下个月出现新的费用类型「偏远费」 | 流程标记失败，说清是哪个新类别、几行、少了多少钱（84.00），文件仍可下载核对；一句话修订后 v2 通过，合计与输入一致 | 约 30 秒 |

实测中发现并修复的问题：修改模式下模型会自己逐行核对人工结果把推理轮数耗光（现在会提醒它交给 `build_recipe`，且最后一轮强制作答）；校验规则参数名写法不统一导致误报「合计对不上」（现在多种写法都认，写错时明确报「规则写错了」）；流程先筛选后汇总时合计校验对不上（新增 `input_filter`）；两张输出表之间对账（新增输出 sheet 作为对比来源）；计划模式只把文字结论带到下一步，导致模型「说了但没做」（现在带上真实的工具调用记录）；同时上传 9 月、10 月两张明细时表名冲突、同类表被拆给多个专员导致无法对比；浮点尾数（341.73999999999995）出现在预览和 Excel 里。

## 已知限制 / 下一步

- 没有管理员给成员分配客户的界面（数据模型和权限检查已经支持，`user_customers` 表）。
- 客户公式只有「新建 / 保存新版本」，界面上没有看旧版本、回退旧版本的入口（旧版本都保留在库里）；试运行的数据只能是客户的文件或粘贴的几行，不能用别的流程的中间表。
- AI 遇到内置公式覆盖不了的逻辑仍然会用 `custom_sql`；客户公式目前由人在表单里维护，AI 不会自己创建。
- 编辑输出依赖 openpyxl，并非支持所有 Excel 特性：检测到控件、切片器、嵌入对象等不支持的内容时停止；涉及公式引用、合并区域、条件格式、数据验证、特殊行样式等的行列重排也会停止，避免静默丢失。旧版 `.xls` 编辑需要先另存为 `.xlsx`，不再降级丢弃格式；CSV 没有工作簿格式，仍可生成普通结果表。程序异常退出或进程被强制终止不在正常临时文件清理保证范围内。
- 读取 Excel 时取公式单元格的缓存值：由程序生成、从没在 Excel 里打开保存过的文件，公式格可能为空。
- 单机本地部署设计（SQLite + 进程内后台任务），多人大并发时需要换 PostgreSQL 和任务队列，接口不用变。
