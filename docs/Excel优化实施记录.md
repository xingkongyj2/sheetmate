# Excel 建表与编辑优化实施记录

日期：2026-11-12。本轮在原有副本写回、声明式建表和隔离计算基础上完成准确性及性能优化。

**已实现的准确性改进**

- 工作区保存内部原始行身份。可信内置操作将行号和数据放在同一次 SQL 中计算，避免随机筛选重跑后身份错位；排序、筛选、去重、计算列等可连续传递身份。同名覆盖采用事务，失败回滚数据、结构及元数据。恢复工作区及子进程快照保留身份。
- 原输入按实际读取顺序建立身份；调用者传入的 DataFrame 必须与原件逐行完全一致才建立身份。输出只接受与当前模板读取批次匹配的身份。自定义 SQL、连接、汇总和一对多展开不按相同行数猜测来源。
- 对原列完整保留、可在末尾增列的输出，按身份移动原单元格及行属性，保留底色、数字格式、批注、超链接、行高、隐藏和分组信息。旧调用方没有身份时，只对能唯一匹配的完整记录识别重排；无法验证的原位置写入明确提示。
- **静态底色跟随记录。** 原表手工涂出的斑马纹在筛选后不一定继续交替，系统不会用前两行样式重新覆盖每条记录。既有测试已改为逐条核对源记录底色。
- 横向合并随行移动。会拆散纵向合并的排序安全失败，不替换原件或已有输出。记录内部的普通公式平移相对引用；跨记录、跨表公式以及条件格式、数据验证、图表等复杂引用明确提示需核对。
- 校验汇总统一采用 `fail > not_evaluated > warn > pass`。规则缺字段、参数错误或异常均算未完成校验；明确写错的输入表不再回退为所有输入。保留原来业务失败和历史不足的语义。
- 新建工作簿拒绝超过 15 位的整数，给出单元格位置，要求编号按字符串输入；不会悄悄转换所有数值为文本。公式增加括号、引号和操作数结构检查，仍由表格软件重算。
- 继承布局时列宽、行高按键合并；重复的相同样式规则保留最后一次，保持覆盖顺序。

**已实现的性能改进**

- 同一次导出复用原件解析，多个工作表及严格/宽松重试共享数据；不同表头配置分别缓存，隐藏表保持隐藏。
- 样式按“原样式＋修改属性”缓存，复用字体、填充、边框和对齐结果。每个单元格的可变样式数组仍独立，避免串改。
- 隔离工具只传输可确定的依赖表，返回新增结果及改变的探测元数据；仍保留未知依赖的全量回退、权限检查、命名预留、版本冲突检测、取消和原子发布。
- 只更新探测元数据时保留查询缓存；过滤写回的集合只构造一次；逐格 `DataFrame.iloc` 改为按行迭代。

**本地对照测量**

以下为本机合成数据，不包含模型、网络和真实业务端到端耗时。建表和导出在同一进程中交替运行 Git HEAD 修改前实现与当前实现，各三次取中位数；运行期间存在其他测试负载，因此结果用于观察量级，不能作为稳定性能承诺。

| 新建 2000 行 × 12 列，整区字体、对齐、填充、边框 | 2.753 秒 | 0.211 秒 | 耗时减少约 92% |

**验证与边界**

已增加建表精度与公式结构、样式覆盖独立性、布局继承、校验状态、工作进程依赖与取消、读取次数、行身份、排序合并及源文件保护等回归测试。

最终完整后端回归：`backend/.venv/bin/python -m pytest backend/tests -q`，**362 passed in 37.50s**，退出码 0。`git diff --check` 通过。测试进程退出时仍打印 DuckDB/nanobind 对象泄漏诊断（32 instances、5 keep_alive records、6 types）；本轮未定位或解决这一原生绑定诊断，不能将断言通过解释为资源泄漏排查完成。

## 第二轮：评审后的补强与后续项落地（2026-11-12）

针对对上一轮改动的审查意见（见本文件之前的评审）做了一次性补强。后端完整回归 **397 passed**。

**准确性**

- 校验：规则本身写错或无法执行时，必需规则（`severity=error`）记为 `not_evaluated` 并阻断；可选规则只记为警告并写明“没有执行”，不再拖垮整次运行。缺历史数据的语义不变。
- 建表编号：`table` 绑定的工作区表里含超过 15 位整数的整列自动按文本写入，并在回执说明；手写 `rows` 仍然拒绝。
- 建表公式：新增函数名白名单（`openpyxl.utils.FORMULAE` 加较新函数表）、较新函数（`XLOOKUP`、`IFS`、`TEXTJOIN` 等）自动补 `_xlfn.` 前缀、跨 sheet 引用必须指向规格里存在的工作表；动态数组函数和 `LET`/`LAMBDA` 写入文件后无法可靠计算，明确拒绝并说明改法。前缀只在写文件时添加，保存的规格保持原样。
- 斑马纹：排序后识别隔行底色并按位置重新交替，人工给个别记录的特殊底色仍随记录移动，并给出提示。
- 行身份：单表 `SELECT`（可带 `WHERE`/`ORDER BY`/`LIMIT`/计算列/窗口列）的 `run_sql` 和 `custom_sql` 步骤也能带行身份；`JOIN`、集合运算、`GROUP BY`、`DISTINCT` 等仍不推断。来源于用户 SQL 的改写是尽力而为，执行不了（如无 `GROUP BY` 的聚合）时回退为普通建表，查询本身不受影响。
- 统一落盘验收（`engine/workbooks/verify.py`）：沿用原格式写出后回读，核对目标工作表的列、行数和逐格值（跳过公式和合并区域的非锚点格），并确认未涉及的工作表（值、合并区域）保持原样；结果并入运行校验，不一致即失败。数据量超过 20 万单元格时只记为“未逐格核对”的警告，不冒充通过。新建工作簿写完后同样回读，与声明不一致则放弃交付。脚本直接生成的 Excel 文件要求能被重新打开。

**性能**

- 小表（行数×列数不超过 40 万）上的 `table_info`、`value_counts`、`column_stats`、`preview_table` 不再启动子进程；大表和会落表的工具仍走可杀死的子进程。
- 读取下推：模板写回只解析需要的工作表。新建文件的登记与载入工作区共用同一次解析。
- 行身份恒等映射使用紧凑存储，大表的元数据读写不再携带 n 个整数。输入加载时的“是否未改动”比较改为向量化快速路径，并且比较异常不再中断运行。
- Recipe 步骤过程文件：结果超过 6 万单元格时直接存 CSV（同样可查看、下载），小结果仍为 XLSX。
- 重复修订产生的同范围样式规则，在不改变最终效果的前提下合并。

**测试中发现并修复的既有问题**

- 请求体积估算 `llm/budget.py` 等 4 处遍历请求体时，把 JSON Schema 里的 `"type": [...]`（`revise_recipe` 的工具定义）当成可哈希值做集合判断，导致**所有带该工具的真实模型请求（修改模式）在发出前崩溃**。假 LLM 测试覆盖不到，真实模型端到端测试才暴露。已修复并加回归测试。
- 上一轮新增的 `_match_unique_records` 在每次同列结构编辑前都全量归一化数据；现在先做向量化预判。

**有意改变的行为（相应测试已更新）**

- `table` 绑定大整数由“报错”改为“自动转文本”；`LET`/`LAMBDA` 由“结构合法”改为“拒绝并给出原因”；自定义 SQL 不再一律“清除行身份”。

**仍未做**

- `preview_table` 在大表走子进程时仍传整表（探测元数据需要完整数据，不能简单截断）。
- 创建后的公式仍没有缓存值，需要重算引擎（如 LibreOffice）才能根治，涉及新依赖。
- 跨记录公式（如累计余额）排序后只有通用提示，没有逐公式列出。
- 常驻工作进程、行身份映射改存工作区内部表（当前 10 万行约 4～5 毫秒/次，50 万行约 23 毫秒/次的开销已通过恒等紧凑存储消除了最常见场景）。

## 第三轮：行身份传递与交付链路（2026-11-12）

**准确性 / 保真度**

- `lookup` 和 `join_tables`（仅 `left` / `inner`）保留左表行身份（`engine/formulas/lineage.py`）：匹配带出列后仍可按原始行改写原表。右表键重复造成一对多展开时，结果不带行身份并给出提示；`right` / `full` 会产生没有左表来源的行，不传递；左表无有效行身份或含 `rowid` 列时同样跳过。
- 保真写回的降级改为按工作表：只有出问题的那张原工作表改用兼容方式，其余工作表仍精确写回，提示里写明是哪张表；无法归因到某张表的错误仍整体降级，行为与之前一致（`template_writer.write_like_original`）。
- 回读校验对超过逐格上限（20 万单元格）、不超过 300 万单元格的工作表改为抽样核对：核对列、行数，并检查首尾各 25 行加 200 个固定种子的随机行。抽样一致只记 `warn`（"没有逐格核对"），抽样发现不一致记 `fail`；超过 300 万单元格仍只确认可打开。
- 多文件交付时指标统计合并所有交付文件，而不是只保留最后一个；统计失败写日志而不是静默吞掉。

**性能**

- 登记交付时每个文件只解析一次，读到的工作表经 `sheet_cache` 复用于指标统计；回读校验的多个工作表共享同一次文件解析；`_has_formulas` 只遍历已存在的单元格。

**第 6 条：交付件硬链接（已完成）**

- 新增 `engine/workbooks/atomic.py`：`atomic_path` 先写同目录临时文件、成功后 `os.replace`；`link_or_copy` 只新建目标（已存在抛 `FileExistsError`，绝不覆盖），优先硬链接，跨文件系统等不支持时退回拷贝。
- `write_excel` 和 Recipe 过程文件的 CSV 写出改为原子替换（`builder` 和 `template_writer` 原本就是）。每次重写都是新的 inode，不会改动指向旧文件的硬链接，这是"已交付文件不可变"的前提。
- `register_delivery_files` 改用 `link_or_copy`。内部文件通常在系统临时目录、与数据目录不在同一文件系统，此时自动退回拷贝，行为与以前一致；同一文件系统上省掉一次整文件拷贝和磁盘占用。

**第 4 条：XML 值补丁（已完成，范围有意收窄）**

- 新增 `engine/workbooks/xml_patch.py`。原件含 openpyxl 载入再保存会丢掉的部件（切片器、表单控件、绘图形状、嵌入对象、自定义 XML）、且编辑只改已有单元格的值时，直接对工作表 XML 做定点替换，其余 zip 条目按字节原样复制；此时不再输出"对象可能变化"的提示。
- 只处理能证明安全的子集，任何一项不满足都返回 `None`、不留下文件，由原有 openpyxl 流程接手并照常提示：
  - 全部输出都是改写原工作表（不追加新表、不重命名），来自同一个 `.xlsx` / `.xlsm`；
  - 行数相同、列完全一致，且有恒等的原始行身份（不靠值猜测）；
  - 被改单元格不是公式、不在合并区内；行里缺失的单元格按列序插入，目标行不存在则不适用；
  - 新值是数字、文本、布尔或空白（日期需要匹配数字格式，超过 15 位的整数需要转文本，都留给原有流程）；数字 5 与文本 "5" 视为不同内容。
- 文本以内联字符串写入，不改 `sharedStrings.xml`，不影响其他单元格或工作表。工作簿里存在公式时在 `workbook.xml` 加 `fullCalcOnLoad`，让 Excel 打开时重算过期的缓存值；没有公式则 `workbook.xml` 不动。
- 补丁后仍走原有的回读校验（`verify_template_output`）。
- **有意没有扩大到所有编辑**：原件没有不支持部件时，仍走经过大量回归的 openpyxl 流程。扩大范围可以另行评估，但会改变全部编辑的底层写法，风险与收益需要单独权衡。
- 仍未覆盖：增删行列、重排、新增列、追加汇总表等结构性编辑；这些在含不支持部件的工作簿上依然会丢失这些部件，并如实提示。

## 第四轮：独立的 OOXML 结构编辑模块（2026-11-12）

把上一轮的 XML 值补丁扩展为独立模块 `engine/ooxml/`，直接修改 .xlsx / .xlsm 内部 XML，未改动的部件按字节原样保留。模块只依赖标准库和 openpyxl 的纯工具（公式分词 / 平移、坐标换算），不依赖 pandas、DuckDB、Recipe 或 Agent。原 `engine/workbooks/xml_patch.py` 已并入并删除。

**模块结构**

| 文件 | 职责 |
|---|---|
| `package.py` | zip 读写：只记录被改动 / 新增 / 删除的部件，保存时其余部件逐字节复制；原子落盘 |
| `sheetxml.py` | 工作表行 / 单元格模型；未改动的行输出原始文本；按类型构造单元格（内联字符串，不动 sharedStrings） |
| `ranges.py` | 工作表尾部范围元素的同步：合并区、条件格式、数据验证、自动筛选、排序状态、超链接、忽略错误、保护区域、分页符 |
| `parts.py` | 表格对象、绘图 / 批注 / 控件的位置保护、定义名称、图表引用、透视表保护、计算链、重算标记 |
| `styles.py` | 只读解析数字格式（百分比 / 日期 / 其他），用于给新列选样式来源 |
| `editor.py` | 对外入口 `OoxmlEditor` / `SheetEditor`：`set_values`、`delete_rows`、`insert_rows`、`reorder_rows`、`save` |
| `engine/workbooks/ooxml_writer.py` | 适配层：结果表 + 原始行身份 → 删行 → 排序 → 改值 → 右侧追加列 |

**原则：不确定就拒绝（`OoxmlUnsupported`）。** 失败时不留下目标文件和临时文件，调用方退回常规流程。

- 删行 / 插行同步：行号与单元格坐标、全部公式（含展开共享公式）、合并区、条件格式 / 数据验证（公式的相对引用按范围锚点平移）、筛选、超链接、表格对象范围、定义名称（含 `_FilterDatabase`）、其他工作表的公式、图表引用；删除计算链并要求重算。
- 排序：整条记录（样式、行属性、超链接、单行合并）随行移动；记录内的公式只允许引用本行或绝对行。
- 拒绝：位于被修改行或其下方的图表 / 形状 / 切片器 / 批注 / 控件、透视表（含以本表为数据源）、数组 / 数据表公式、引用已删除单元格的公式、只覆盖排序区一部分的范围、跨行合并区被部分删除或排序、表格对象表头被删或无数据行、右侧追加列时工作表含表格对象、日期 / 超过 15 位整数 / 比例新列。
- 新增列的样式只向「同数据类型、数字格式不会把值显示错」的原列借，借不到就不设样式；这是回读校验发现问题后修正的（最初沿用左邻列样式，数字被显示成 1900 年日期）。

**启用方式**：`.env` 的 `OOXML_EDIT`：`auto`（默认，原件含 openpyxl 会丢失的对象时启用）/ `always` / `off`。`write_like_original` 先尝试 OOXML 路径，成功则不再给“对象可能变化”的提示，失败则走原有流程。

**验证**

- 新增 `tests/test_ooxml.py`（模块本身）、`tests/test_ooxml_writer.py`（适配层与开关），并更新 `test_template_output.py` 的两处过时断言（追加列已被支持，改用追加汇总表作为仍会警告的结构变化，另加删行保留控件的端到端用例）。
- 全量回归在默认模式和 `OOXML_EDIT=always` 下各跑一遍，后者让所有可处理的既有编辑场景都走新路径，用来发现行为差异；两种模式均全部通过。
- 5 万行、4 万个公式、删 20% 行并改值：OOXML 路径约 2.8 秒，常规流程约 19.9 秒，输出大小相当。

**边界与未验证**

- 没有用真实 Excel 生成的复杂文件（带切片器 / 透视表 / 共享公式的业务表）验证；测试用 openpyxl 生成并注入部件。没有 Excel 或 LibreOffice 做“能否正常打开”的冒烟检查，只做了 XML 合法性和重新解析。建议用几份真实业务表在 `always` 下试跑。
- 图表缓存值、透视表缓存不会更新；位于改动区域的图表 / 透视表一律拒绝而不是改写。
- `test_formula_free_xlsx_fast_path_matches_the_full_path` 出现过一次偶发失败（该测试只调用读取器，与本次改动无关，之后重复运行均通过），未定位原因。

## 第三轮：按用户意图改原表（增、删、改、加列）的准确与速度（2026-11-12）

目标：新增、删除、修改任意组合时内容准确、速度快，新增内容的样式与原表一致。全量回归 **310 passed**。

**写回层（`template_writer.py` 等）**

- 按记录对齐：结果与原表逐行对齐为“没变 / 改了 / 新增 / 删除”，没变的行原样不动（格式、批注、行高都在），删除按 Excel 的方式删行并调整引用，新增行插到正确位置，改过的行只改变化的单元格。
- 行引用映射泛化为删行与插行两种（`row_references.py` 的 `InsertedRows`）：在数据区末尾追加时，恰好止于末行的区域引用（如 `SUM(C3:C10)`）一起扩展；单个单元格引用不扩展。
- 样式画像：新增行取全部数据行的“众数样式”，不再只看前两行；识别隔行斑马纹，新增行和重排后的行按位置交替，个别手工标色的行随记录走。新增列按语义向“样子最像”的原列借样式（比例列借百分比格式、金额类借金额格式），带时间的值不被纯日期格式遮住，整行标红时新列单元格同色。
- 页脚合计行：读取层识别数据区下方的“合计 / 总计 / 小计”行，不再当作数据（避免重复统计），写回时随数据区移动，`SUM` 范围自动调整。列结构变化走“整块重建”分支时，会先记下页脚，数据写完后按新的列位置、新的数据行数放回，公式的列引用与行范围一并改写（此前该分支会把表头以下所有行连合计行一起删掉）。

**新增 `append_rows` 公式**：追加几条记录走 Recipe 与写回层，不再逼模型写脚本。值按列类型转换（支持 `10%`、千分位、`2026年11月9日`），转换失败时指出是哪一列、什么值。

**真实模型验证中查到并修复的问题**

| 问题 | 现象 | 修复 |
|---|---|---|
| 完成核对反复否认已完成的修改 | 流程成功、校验全过，但完成核对的本地规则连续多次判定“数据不完整”，轮次耗尽后**没有交付文件**；追加场景 82～262 秒 | 根因：合计行的公式没有缓存值（本系统和 openpyxl 生成的文件都如此），整张表被标成“公式缓存缺失”。页脚行里缺失的缓存不再计入数据质量；数据区里的仍照常报出。修复后同场景 **25～26 秒**，2 次工具调用 |
| 模型自己再追加一行合计 | 合计翻倍、校验失败后退回写脚本 | 表概要和流程生成提示都说明“页脚合计行会被保留，不要再追加” |
| 追加记录后“合计不变”校验误判 | 期望值没算追加的金额 | `sum_preservation` 把 `append_rows` 追加的数值合计计入期望值 |
| 修改金额时模型写了“合计不变”规则 | 同一条校验失败 5 次，178 秒 | 提示词要求：改动数值列时不要对它写合计对账；修复后 **23.5 秒** |
| 日期列有空值时预览崩溃 | `NaTType does not support strftime`（既有缺陷） | `to_jsonable` 先排除 `NaT` |
| `build_recipe` 被多余的“写出工作簿”步骤拒绝 | 整个流程判不合法 | 报错提示明确“删除这一步，系统会自动写出”，提示词同步说明 |
| 缺 `table` 参数的步骤 | 整个流程判不合法 | 只有一个输入表时默认接上一步输出，多个输入表不猜 |
| “整列为空”警告 | 原表本来就空的备注列也报警告，误导模型继续折腾 | 输入里就是空的列不再警告 |
| 验收把计划末尾的“合计”行误报行数不符 | `verify_sheet` 假失败 | 末尾行按位置一起核对 |

**读取速度**：xlsx 无公式文件跳过第二遍解析（5 万行约 2.6s → 1.4s）；CSV 分隔符明确时走 C 引擎（5 万行 0.63s → 0.04s）。
